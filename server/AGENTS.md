# Соглашения по серверу

Правила этого модуля. Общие для всего репозитория — в корневом `AGENTS.md`,
подробности про запуск, схему и сид — в `server/README.md`.

## Команды

Выполняются из `server/`:

```bash
mvn verify             # сборка и тесты; модели API генерируются на лету
mvn spring-boot:run    # запуск против своей базы
docker compose up      # база и сервер; инструкция в server/README.md
```

Перед завершением: `mvn verify`.

## Тесты

**Три уровня. Уровень выбирается по цене подделки, а не по привычке.**

| Уровень | Суффикс файла | Что поднимается | Чем проверяется |
|---|---|---|---|
| **1. Быстрый** | `*Unit` | ничего, чистый JUnit + моки | правила, отказы, порядок проверок D32 |
| **2. С контекстом** | `*Test` | Spring-контекст, хранилище подменено моками | advice, тело ответа через Jackson, `@Valid`, маршруты |
| **3. Интеграционный** | `*IT` | контекст + настоящий Postgres в Testcontainers | ограничение под гонкой, явный `flush`, настоящие SQL-ошибки |

**Уровень — это суффикс имени файла, меток нет намеренно.** `*Unit` гоняет
surefire первым, `*Test` — вторым, `*IT` — failsafe фазой позже. Забытая
аннотация `@Tag` молча выкинула бы тест из прогона; неверный суффикс видно
глазами. Порядок тот же, что и у цены: падение дешёвого уровня останавливает
сборку до подъёма контейнера, и сразу видно, что сломалось — правило или база.

**Правило перехода:** если тест уровня 3 можно написать на уровне 1 или 2
**без потери смысла** — пишем там. Обратное запрещено: поднимать контейнер
«на всякий случай». Критерий выбора — «можно ли дешёвой подделкой обойтись», а не
«насколько тест сложный». HTTP-граница (маршруты, `@Valid`, коды и тела ответов)
моками проверяется полностью — это уровень 2, а не 3.

**Отдельного теста на миграции и схему нет.** Любой тест уровня 3 поднимает
контекст, а на старте работает `ddl-auto: validate`: если Liquibase не создал
таблицу или создал не ту, что ждёт Hibernate, контекст не поднимется и упадёт
первый же IT. Проверять «схема соответствует» ещё одним классом — платить за
второй контейнер за наблюдение, которое уже даёт старт контекста.

**Уровни 1 и 2 обязаны быть быстрыми.** Дорогая часть `mvn verify` — контейнер и
сборка Spring-контекстов, поэтому каждый тест уровня 3 должен уметь назвать, что
именно он покупает за контейнер. Разбор пирамиды — #102.

**H2 не подходит** как подмена хранилища: сервер на PostgreSQL, а `tstzrange`
и `EXCLUDE USING gist` в H2 не воспроизвести. Либо моки на репозиториях, либо
Testcontainers.

**Контейнер один на весь прогон** (`SharedPostgres`), стартует лениво и не
гасится: JUnit к нему не причастен (`@Container` не ставится), уборку делает Ryuk
на выходе JVM. Отсюда следствие, которое обязаны держать все интеграционные тесты:
**состояние базы общее** — тест чистит за собой перед каждым своим тестом, потому
что соседний класс мог оставить строки. Тест, полагающийся на чужой порядок,
должен падать, а не «иногда проходить».

**Отказ хранилища (умершая база) на уровне 3 не проверяется вовсе** — решением
владельца наблюдение снято. Белый список D38 проверяется на уровне 2
поведенчески, по всем семи механизмам (`ApiAdviceTest`), а сама целостность —
на уровне 3, на живой базе (`ApiOperationsIT`).

## Зависимости

- **Внедряем зависимости через конструктор**: поля объявляем `final`,
  зависимости передаём параметрами конструктора. `@Autowired` в основном коде
  не используем — ни на полях, ни на конструкторе: у бина с единственным
  конструктором он не нужен.
- **Lombok в проекте нет.** Если конструктор скучный, пишем его руками, а не
  добавляем `@RequiredArgsConstructor` в `pom.xml` под одну аннотацию.
- **В тестах `@Autowired` на поле допустим** — см. `ApiOperationsIT`.

## Подводные камни

- **В Spring Boot 4 автоконфигурация Liquibase вынесена в отдельный модуль
  `spring-boot-liquibase`, и `starter-data-jpa` его не тянет.** Без этой
  зависимости `liquibase-core` лежит на classpath, но автоконфигурация в
  контекст не попадает: миграции молча не выполняются, схемы нет, а
  приложение стартует. Обнаружится это только на первой попытке обратиться к
  таблице.
- **Тесты привязывают контейнер через `@ServiceConnection`.** Собственный
  `@DynamicPropertySource` не подойдёт: он вызывается при сборке контекста,
  когда контейнер ещё не стартовал, и Spring падает с «Mapped port can only be
  obtained after the container is started».
- **Локальный Maven может быть 3.6.x, а сервер требует 3.9.x.** Сборка идёт
  через Docker-образ `maven:3.9-eclipse-temurin-25`, который зашит в
  `server/Dockerfile`; при расхождении версий проверяйте сборку в этом образе.
- **Модели API генерируются в каждой сборке** из
  `vite-project/contract/openapi.yaml` (коммитится, Node не нужен). Плагин в
  дефолтном билде намеренно: с импортом `api.model` слоями `mvn verify` без
  моделей не идёт, а профиль это только прятал. Контракт правится в
  `vite-project/main.tsp`, потом пересобирается (`npm run contract` во фронте).
- **Генератор требует двух флагов, которые молча игнорируются рядом.**
  `useBeanValidation` и `documentationProvider` живут в `configOptions`, а не
  среди параметров плагина; вне `configOptions` D40 (@Size/@Pattern) работает
  «вроде бы», а `swagger-annotations` тащится на classpath. `generatorName:
  java` — не наш: это клиентские модели под Gson.
- **Миграции лежат в папке версии** (`src/main/resources/db/changelog/0.0.1/`).
  Папка названа версией `pom.xml`, в чей релиз попали её changeset'ы; правку в
  уже выпущенную папку не добавляют.
