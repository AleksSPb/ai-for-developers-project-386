# Сервер календаря бронирования звонков

Серверная часть сервиса: Java 25, Spring Boot 4.1.1, Maven, PostgreSQL, Liquibase.
Контракт — [`vite-project/main.tsp`](../vite-project/main.tsp), он же источник
правды для всего, что сервер отдаёт.

## Что здесь пока есть

**Локальный запуск, схема базы и все семь операций контракта.** Работают
`GET /windows`, `GET /event-types`, `GET /event-types/{id}`,
`POST /event-types`, `PATCH /event-types/{id}`, `GET /bookings` и
`POST /bookings`.

Работающие операции — это весь домен, а не «начало»: запись проходит
пять шагов порядка, гонка двух Гостей за слот даёт ровно один `201` и ровно
один `409`, а отказ хранилища отличается от занятого слота не только кодом,
но и разбором по месту: имена ограничений базы читает слой правил, пока
транзакция открыта. Подробности раскладки — в `package-info.java` пакета
`com.hexlet.calendar`.

**Клиент работает с этим сервером**, если ему задан адрес
(`VITE_API_BASE_URL`, см. [корневой README](../README.md)); без адреса он, как и
раньше, отвечает себе рукописными заглушками. Обе двери открыты: заглушки
нужны, чтобы видеть интерфейс и гонять тесты без базы.

## Локальный запуск

```bash
cd server
cp .env.example .env      # необязательно: compose поднимается и на умолчаниях
docker compose up --build
```

Поднимаются два сервиса: `db` (PostgreSQL 18) и `server` (Java, порт 8080).
Сервер ждёт готовности базы — healthcheck `pg_isready`, а не «процесс запустился»,
иначе Liquibase стартует раньше, чем база встала.

Порт сервер читает из `SERVER_PORT`, затем из `PORT` и только потом берёт 8080.
Второе имя задают площадки и автоматическая проверка курса: она запускает
контейнер с `PORT=8080` и ждёт `200` на главной странице. Для проверки в корне
репозитория есть свой `Dockerfile`: тот образ собирает ещё и клиент и поднимает
базу внутри себя, потому что базы проверка не даёт ([ADR-0009](../docs/adr/0009-self-contained-image.md)).

## Откуда приходит клиент

**Сервер пускает не всякого.** Клиент раздаётся Vite с
`http://localhost:5173`, а сервер отвечает с `http://localhost:8080` — для
браузера это два разных источника, и без разрешения он отбрасывает ответы:
`GET` молча, а `POST /bookings` и `PATCH /event-types/{id}` ещё и на
предварительном запросе (D61).

Разрешённые адреса — свойство `cors.allowed-origins` в `application.yml`,
список через запятую, по умолчанию `http://localhost:5173`. Переопределяется
переменной `CORS_ALLOWED_ORIGINS` (проброшена в `compose.yaml`):

```bash
CORS_ALLOWED_ORIGINS='http://localhost:5173,http://localhost:4173' docker compose up
```

Здесь **не** `*`: пустая строка вместо адреса открыла бы запись в календарь
любому сайту, чей гость открыл страницу. Разрешены ровно те методы и тот
заголовок, что описаны контрактом, а куки и авторизация не участвуют вовсе.

Если Vite занял другой порт (например, 5173 уже занят и он взял 5174), сервер
ответит «нет, ты не разрешён» — и это будет выглядеть как пустой календарь.
Адрес Vite надо либо указать в `CORS_ALLOWED_ORIGINS`, либо запустить на
`--port 5173 --strictPort`.

Остановить, не теряя данные:

```bash
docker compose down
```

Снести вместе с базой:

```bash
docker compose down -v
```

Свою `.env` compose читает сам, отдельный `--env-file` не нужен.

## Кто выполняет миграции

**Сервер, при своём старте.** Отдельной команды и отдельного сервиса миграций
нет: `compose.yaml` остаётся из двух сервисов, и не появляется третий, который
надо отдельно дождаться и отдельно диагностировать.

**Что происходит при недоступной базе: приложение не поднимается вовсе.** Оно
падает на старте с ошибкой подключения и ненулевым кодом выхода, а не отвечает
`503`. Сделано так намеренно: поднявшееся приложение с недоступной базой
выглядело бы рабочим, и отличать его от исправного пришлось бы по кодам ответа.
Пока сервер не поднялся, его неисправность видна сразу — по логу и по коду
выхода.

Отсюда же следствие для эксплуатации: `503 service_unavailable` в контракте
означает отказ хранилища **после** старта (база отвалилась, когда сервер уже
работал), а не при старте. Перечень причин — не супертип, а белый список
(D38): нет соединения, оборвалась транзакция, истёк `statement_timeout`.
Нарушения целостности в список не входят, иначе гонка за слот раздулась бы
в `503`.

## Таймауты

Все три величины живут в `application.yml`, рядом с настройками пула:

| Величина | Значение | Что ограничивает |
|---|---|---|
| `hikari.connection-timeout` | 5 с | ожидание соединения (D60) |
| `statement_timeout` | 10 с | выполнение запроса в базе |
| `lock_timeout` | 2 с | ожидание блокировки |

Последние два задаются через `connection-init-sql` — **именно `SET`, а не
`SET LOCAL`**: `SET LOCAL` сбрасывается на конце транзакции, и величины
действовали бы только внутри той транзакции, которая их задала.

`lock_timeout` меньше `statement_timeout` не по вкусу: проигравшая гонка за
слот ждёт **блокировку**, а не выполняет долгий `SELECT`. Без `lock_timeout`
сработал бы `statement_timeout` и отдал `503` вместо `409`.

## Режим без сида

Сид окон лежит в changeset'е с контекстом `seed`. Пустой `LIQUIBASE_CONTEXTS`
(по умолчанию) выполняет всё, включая сид; `!seed` создаёт схему и не заводит
окна:

```bash
LIQUIBASE_CONTEXTS='!seed' docker compose up
```

Нужен для двух случаев:

- **«База пуста, гость видит пустой календарь»** — состояние, в котором сервер
  окажется сам через 14 дней после сида, но до него доходит только по
  возвращении. В тестах это состояние нужно уметь воспроизвести, а не ждать.
- **Чистая таблица для тестов.** Тесты сидят на фикстуре, а не на changeset'е
  сида: даты в changeset'е относительные, и через полгода он заведёт совсем
  другие окна, чем проверяет тест.

Тот же переключатель работает и без Docker — через переменную окружения при
`mvn spring-boot:run`.

## Сид окон

14 дней вперёд, 09:00–18:00 Europe/Moscow, по окну в день.

Даты считаются **относительно** — от `now()` самой базы, поэтому changeset
остаётся верным через полгода после написания. Он и применяется один раз:
Liquibase держит свою таблицу `DATABASECHANGELOG`, и повторный запуск на ту же
базу не заводит окна заново.

Окна заведены целиком, включая сегодняшнее, и оно окажется в прошлом уже завтра.
За это отвечает правило «окно, целиком закончившееся, не возвращается».

Сид использует **часы базы**, а сервер в остальном живёт по часам JVM. Расхождение
возможно и принимается — на локальном запуске это незаметно, а в тестах сид не
участвует.

**Календарь пустеет через 14 дней.** Живое продление окон не придумано: после
истечения сида `GET /windows` вернёт пустой список, и гость увидит пустой
календарь. Это зафиксированный факт, а не баг, и он касается `README` в корне
(см. решение D59).

## Сида типов событий нет

Сид заводит **окна**, и только их. Типов событий в базе не остаётся ни одного, а
без Типа записаться не на что и выбирать нечего: страница выбора покажет
пустоту, и это будет выглядеть как поломка.

Первый Тип заводится руками — в разделе Владельца (`/#/event-types`) или
запросом:

```bash
curl -X POST http://localhost:8080/event-types \
  -H 'Content-Type: application/json' \
  -d '{"id":"consult","name":"Консультация","description":"Разговор о делах","durationMinutes":30}'
```

## Схема

Liquibase создаёт схему, Hibernate её не трогает: `spring.jpa.hibernate.ddl-auto`
равен `validate` — Hibernate только проверяет, что схема совпадает с
ожиданиями, и падает на старте при расхождении.

Миграции разложены по папкам версии — `db/changelog/0.0.1/` и далее. Папка
названа той версией `pom.xml`, в чей релиз попали её changeset'ы.

Три таблицы:

| Таблица | Что в ней |
|---|---|
| `windows` | окна приёма: `start_dt`, `end_dt` |
| `event_types` | типы событий: `id` (slug, `varchar(40)`), название, описание, длительность |
| `bookings` | брони: интервал, имя и почта гостя, время создания |

Пара ограничений, которые стоит знать до написания кода:

- **`bookings.event_type_id` — `varchar(40)`, а не `uuid`:** внешний ключ на
  `event_types.id varchar(40)` требует совпадения типов, и `uuid` со
  `varchar(40)` в PostgreSQL не собирается.
- **Пересечения Броней запрещены на уровне базы** — `EXCLUDE USING gist` по
  `(event_type_id, tstzrange(start_dt, end_dt, '[)'))`. Это единственное место,
  где рождается `409 slot_taken` при гонке двух гостей, поэтому проверять
  пересечение в коде сервера обязательно, а база — последний рубеж.
- **Дублей окон база не защищает:** уникального индекса на `start_dt` нет
  сознательно, единственный барьер — сама миграция. Руками создать два окна с
  одинаковым началом можно, и `GET /windows` вернёт оба.

## Метрики

Сервер отдаёт стандартные HTTP-метрики actuator'а и три счётчика успешных
операций домена. Эндпоинты живут на порту 8080 рядом с операциями контракта и в
сам контракт (`vite-project/main.tsp`) **не входят**.

```bash
curl http://localhost:8080/actuator/metrics
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/loggers/com.hexlet.calendar
curl http://localhost:8080/actuator/env
```

| Эндпоинт | Что в нём |
|---|---|
| `health` | состояние приложения и компонентов; с `show-details: always` видно и базу |
| `metrics` | имена и значения метрик, `/actuator/metrics/<имя>` — по одной |
| `info` | пусто: своих сведений сервер пока не публикует |
| `env` | имена свойств и источники; **значения скрыты** (`show-values: never`) |
| `loggers` | уровни логирования; **только чтение** |

Три счётчика домена считают то, чего actuator не считает: HTTP-метрики видят и
отказанные запросы, и идемпотентные повторы, создавшие ноль строк.

| Метрика | Что означает |
|---|---|
| `booking.created` | записана новая Бронь |
| `event_type.created` | заведён новый Тип события |
| `event_type.updated` | вызвано переименование Типа события |

Идемпотентные повторы (`POST /bookings` с тем же ключом, `POST /event-types` с
тем же набором полей) в счётчики **не попадают**: строка не создавалась.
Переименование считается всегда, включая вызов с теми же значениями полей, —
счётчик меряет вызовы, а не различия в данных.

```bash
curl -X POST http://localhost:8080/event-types \
  -H 'Content-Type: application/json' \
  -d '{"id":"consult","name":"Консультация","description":"Разговор о делах","durationMinutes":30}'

curl http://localhost:8080/actuator/metrics/event_type.created
```

**`exposure.include` и `access` отвечают на разные вопросы.** Первое — *что
видно* наружу (список эндпоинтов), второе — *что с этим эндпоинтом можно
делать*: `access: read-only` читает, но не даёт менять. Так `loggers` показывает
уровни, а `POST` на смену уровня отвечает `405`:

```bash
curl -X POST http://localhost:8080/actuator/loggers/com.hexlet.calendar \
  -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'
# 405 Method Not Allowed
```

Список эндпоинтов перечислен явно, а не задан как «всё, кроме опасного»: иначе
следующая версия Boot открыла бы наружу то, о чём здесь не думали.

Значения свойств в `env` скрыты не из осторожности, а потому что в
`application.yml` есть `POSTGRES_PASSWORD`: имена нужны, чтобы понять, какое
свойство не применилось, а значение показывать незачем. Всё это **не защита**:
эндпоинты actuator'а не ограничены `cors.allowed-origins` (D61), так что держите
их на порту, недоступном извне.

`HEALTH_SHOW_DETAILS` переопределяет глубину `health`; по умолчанию `always`.

## Разработка

Команды выполняются из `server/`:

```bash
mvn verify             # сборка и тесты
mvn spring-boot:run    # запуск против локальной базы
```

Для `mvn spring-boot:run` нужна своя PostgreSQL — из `compose.yaml` поднимется
только база:

```bash
docker compose up db
mvn spring-boot:run
```

Тесты поднимают PostgreSQL в Testcontainers сами, база для них не нужна.
Контейнер привязывается к Spring через `@ServiceConnection`: свой
`@DynamicPropertySource` не подойдёт — он вызывается при сборке контекста, когда
контейнер ещё не стартовал.

Модели API генерируются из `vite-project/contract/openapi.yaml` на каждой
сборке — отдельной команды нет. Контракт закоммичен, Node для сборки сервера
не нужен: он нужен только чтобы пересобрать сам контракт из `main.tsp`.

Требуется Maven 3.9.x (в системном 3.6 сборка не идёт) и Docker — ради
Testcontainers.
