# Доменные доки

Как инженерные скилы должны читать доменную документацию этого репозитория при исследовании кодовой базы.

## Перед исследованием прочитать

- **`GLOSSARY.md`** в корне репозитория, либо
- **`GLOSSARY-MAP.md`** в корне репозитория, если он есть: он указывает на по одному `GLOSSARY.md` на контекст. Читайте те, что относятся к теме.
- **`docs/adr/`**: ADR, которые затрагивают область, с которой собираетесь работать. В мультиконтекстных репозиториях дополнительно проверяйте `src/<context>/docs/adr/` — решения в рамках контекста.

Если каких-то из этих файлов нет, **продолжайте молча**. Не сообщайте об их отсутствии и не предлагайте создать их заранее. Скил `/domain-modeling` (через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно проясняются.

## Структура файлов

Раскладка в этом репозитории — single-context:

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
└── vite-project/
```

Мультиконтекстный вариант (если в корне появится `GLOSSARY-MAP.md`):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← общесистемные решения
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения в рамках контекста
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Использовать словарь глоссария

Когда в вашем выводе называется доменное понятие (в заголовке задачи, в предложении рефакторинга, в гипотезе, в имени теста), используйте термин в том виде, как он определён в `GLOSSARY.md`. Не заменяйте его синонимами, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет, это сигнал: либо вы вводите язык, которого проект не использует (пересмотрите), либо есть настоящий пробел (отметьте его для `/domain-modeling`).

## Сообщать о конфликтах с ADR
